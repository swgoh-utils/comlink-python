    Phase 8 — Ergonomics: streaming, raw_request, healthcheck¶

    Branch: v3/phase-8-ergonomics (off v3.0-dev)

    Status: complete; ready to merge.

    Adds three operator-friendly methods to both clients, plus documents the async-StatCalc deferral. No performance headline; the win is "the SDK gives you the right shape for the right job."

    Scope delivered¶

    • [x] healthcheck(timeout=5.0) -> bool — probes /enums with a short timeout. Returns True on 200, False on any error. Does NOT retry, does NOT raise. Sync + async parity.
    • [x] raw_request(method, path, payload=None) -> httpx.Response — escape hatch. HMAC headers still attached; everything else (retry, classify, decode, struct dispatch) bypassed. Caller gets the raw response.
    • [x] stream_game_data(...) and stream_localization(...) — return an httpx.Client.stream / AsyncClient.stream context manager. Caller iterates iter_bytes() (sync) or aiter_bytes() (async). Bypasses retry (a half-streamed response can't be replayed cleanly).
    • [x] tests/v3/test_ergonomics.py — 18 tests covering each method × sync + async, plus error paths (5xx, timeout, connect error, retry bypass, HMAC headers).
    • [x] All 742 tests green; coverage stays ~96%.

    Deviations from the plan¶

    Plan said Reality Why
    stream=True kwarg on get_game_data() / get_localization() Separate methods: stream_game_data() / stream_localization() A stream=True kwarg would make get_game_data's return type dict \| Struct \| ContextManager[Response] — the type narrowing logic gets ugly for callers and type-checkers. Separate methods give clear return-type contracts. Same user value, cleaner API.
    Async-aware StatCalc with threshold-based ProcessPoolExecutor switching Skipped — deferred to v3.1. Touching StatCalc/ for the third time in a row (Phase 3.5, Phase 7, Phase 8) would have churned a subpackage the v3 phases have consistently kept out of scope. The pattern is intentional: the StatCalc internals carry no v3 architectural debt — they work as-is with the new client surface. Add async-aware execution in a focused v3.1 phase.
    stream_game_data() (async) resolves version="" via metadata fallback Async stream_game_data requires explicit version= The metadata fallback in the sync version calls self._get_game_version() synchronously. The async equivalent would need to be async def (returns a coroutine, not a stream). Forcing the version to be explicit keeps the method synchronous-returning-an-async-context-manager — which is what async with client.stream_game_data(...) semantics requires. Documented in the docstring.

    Headlines¶

    No perf headline. The three methods are about shape — giving callers the right tool when the default request path doesn't fit:

    • healthcheck turns a startup-probe pattern that used to be 6 lines of try/except into one bool-returning call.
    • raw_request lets callers escape the retry / decode pipeline for custom endpoints or debugging without forking the SDK.
    • stream_* holds memory flat regardless of payload size (the ~80 MiB JSON /data blob streams chunk-by-chunk instead of materializing).

    Behavior preserved¶

    • All existing endpoint methods (get_player, get_guild, etc.) unchanged.
    • Retry behavior on the typed/default path unchanged.
    • compat, _cache, _optional, _payloads, _models, _retry all unchanged.

    Open questions / carry-forward to v3.1¶

    • Async-aware StatCalc. Plan target: calc_roster_stats_async picks asyncio.to_thread for small rosters and ProcessPoolExecutor for large ones. The threshold needs an honest benchmark across roster sizes {10, 50, 100, 250, 500}; that benchmark IS in scope but the StatCalc rewrite isn't a Phase 8 thing.
    • stream_* retry-on-fail. Currently no retry on streaming. Some operators want "if the stream drops, restart from byte 0". The honest way is to expose a restart_on_error=True kwarg that re-fetches on httpx.ReadError mid-stream. v3.1 candidate.

    Phase 8 exit criteria check¶

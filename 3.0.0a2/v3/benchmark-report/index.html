    v3 Benchmark Report¶

    Consolidated v2.0.x baseline vs v3.0 final numbers across every phase. Raw JSON results live in benchmarks/v3/results/; this document is the human-readable summary.

    All numbers measured on the same machine: macOS aarch64, Python 3.11.15 (uv-managed), 16-inch MacBook Pro M-series. Same comlink cassettes (recorded Phase 0) used as inputs throughout. Timings are medians of N=10–50 iterations depending on the bench; cold-import numbers are particularly noisy on a working laptop (documented in the Phase 0/1 reports' "open questions" sections — variance can be 30–50% run-to-run from system load).

    httpx loaded on import True False (Phase 5)

    Phase 2 — Resilience layer¶

    bench_retry_overhead: −1.10 % overhead with max_retries=3 vs 0 on the happy path (target <2 %).

    bench_retry_recovery: 429 + Retry-After: 1 → 200 takes 1.011 s wall (expected ~1.0 s). 503 (no header) → exp-jitter wait ≈ 0.35 s.

    Phase 3 + 3.5 — msgspec.Struct typing¶

    Best-case wins on player_large after Phase 3.5 deep typing:

    Bench v2 (json) v3 typed win
    bench_decode_speed (player_large) 16.8 ms 6.3 ms 2.67× faster
    bench_decode_speed (player_small) 0.18 ms 0.07 ms 2.49× faster
    bench_decode_memory (player_large peak) 17.7 MiB 9.7 MiB 1.83× lower
    bench_decode_memory (player_small peak) 0.31 MiB 0.13 MiB 2.45× lower
    bench_object_size (player_large resident) 14.4 MiB 10.0 MiB 1.43× smaller
    bench_object_size (player_small resident) 0.25 MiB 0.13 MiB 1.94× smaller

    Plan's original projection was 3–5× faster + 4–6× lower memory + 40–60% smaller object size. Phase 3.5 closed most of the gap; the remaining shortfall is from fields still typed as dict[str, Any] (uniformly empty/null in the cassettes — equipment, unit_stat, Mod.converted_item).

    /data decode speed: 1.00× (no improvement). Documented in phase-3 report as the partial-typing tradeoff — /data segments aren't deeply typed (deferred to Phase 7's GameDataCache and beyond). Object size for /data actually worsens 9% with msgspec untyped — msgspec's dict graph is marginally heavier than json.loads in this specific case.

    v3.1 — typed /data segment coverage¶

    Runs on v3.1-research (not v3.0-dev — v3.0 surface is frozen per Phase 9 / ADR-0004). Hand-types 14 of /data's ~80 segments and measures dict-vs-typed decode for each. Helper: swgoh_comlink.compat.decode_segment (single generic entry point, no per-segment wrappers).

    Bench: benchmarks/v3/bench_data_segments_typed_vs_dict.py. Result JSON: benchmarks/v3/results/phase-v3_1-data-segments.json. Bytes-based on both sides (matches the units-only probe's methodology — apples to apples; msgspec.json.Decoder() vs msgspec.json.Decoder(list[T])).

    Cassette: same data.json.gz used elsewhere in this report.

    Per-segment (typed/dict ratios; <1 = typed is faster/lighter):

    Segment Count Speed (×faster) Memory ratio Size ratio
    units 11,169 4.16× 0.64× 0.66×
    effect 60,015 1.85× 0.49× 0.49×
    statMod 288 1.72× 0.56× 0.57×
    material 858 1.59× 0.59× 0.59×
    datacronAffixTemplateSet 722 1.51× 0.71× 0.71×
    skill 1,892 1.50× 0.49× 0.50×
    equipment 698 1.50× 0.57× 0.58×
    recipe 2,172 1.48× 0.54× 0.54×
    datacronTemplate 61 1.43× 0.61× 0.61×
    statModSet 8 1.25× 0.56× 0.55×
    ability 6,465 1.12× 0.79× 0.79×
    datacronSet 10 1.04× 0.75× 0.76×
    campaign 16 1.04× 1.00× 1.00×
    datacronHelpEntry 5 1.00× 0.56× 0.53×

    Aggregate across all 14 segments:

    Metric dict typed ratio
    Decode wall (sum) ~3,290 ms ~1,840 ms 1.79× faster
    Peak alloc (sum) ~3.5 GiB ~2.3 GiB 0.66×
    Resident size (sum) ~3.5 GiB ~2.3 GiB 0.66×

    Decision rule (pre-registered in the bench script, identical to the units-only probe): - speed_ratio ≥ 1.5× AND memory_ratio ≤ 0.7× → green-light typing remaining segments. - speed_ratio < 1.2× OR memory_ratio > 0.9× → stop here. - In-between → judgment call.

    Outcome: aggregate 1.79× faster AND 0.66× memory — both thresholds met → green-light typing the remaining ~70 /data segments in a follow-up v3.1 phase if operator demand warrants.

    Where the typing didn't move the needle: - campaign (1.04× speed, 1.00× memory). 16 entries, but each has a deeply nested campaignMap.campaignNodeDifficultyGroup.campaignNode list that v3.1 leaves as dict[str, Any]. The bulk is in the un-typed sub-tree; typing only the outer envelope barely helps. Deep-typing the campaignNode shape is a future-phase candidate. - ability (1.12× speed). Same story — aiParams, synergy, visualTarget, tier, descriptiveTag left as dicts because their shapes are sparse / inconsistent across the 6,465 entries. - Very small segments (statModSet, datacronSet, datacronHelpEntry). Decode times are sub-millisecond; ratios are noisy and not meaningful.

    Caveat: the helper's runtime path uses msgspec.convert on dicts (no JSON re-encode), since callers operate on dicts from GameDataCache or get_game_data. The bench's bytes-based comparison isolates the decoder cost. Real-world cost on the cached path is lower than the bench numbers because msgspec.convert walks the in-memory dict tree directly.

    v3.1 — typed/dict client split + codegen¶

    Restructures the public surface into two import paths (swgoh_comlink.* = dict-default; swgoh_comlink.typed.* = typed-Struct default) and code-generates all four client classes (sync/async × dict/typed) from a single manifest. See docs/adr/0005-typed-dict-client-split.md and docs/v3/codegen.md.

    Metric Before (v3.0) After (v3.1-research) Δ
    Cold import swgoh_comlink 7.0 ms 7.8 ms +11% (still well under Phase 5's headline)
    Public client classes 2 4 sync/async × dict/typed
    Hand-maintained endpoint method bodies 32 (2 clients × 16) 0 (all generated from manifest) full elimination
    Manifest entries (single source of truth) n/a 15 one entry per uniform endpoint
    Hand-written escape hatches 8 (per-client) 5 (per surface, in mixins) shared across dict/typed
    Codegen invariant tests 0 107 guards the 2×2 surface contract

    No runtime behavior changes — the four generated clients call the same _post / _request / _retry paths Phase 4 + Phase 2 set up. The codegen lets all four track a single manifest entry per endpoint so a schema change ripples through every variant atomically.

    v3.1 — async-aware GameDataCache¶

    GameDataCache grows a* twins of every client-touching method (acurrent_version, aget_game_data, aget_localization, aevict_old_versions, aclose) and an async with lifecycle. Blocking diskcache and msgpack ops run on asyncio.to_thread; in-memory hits stay synchronous. Same disk store and memo as the sync surface — a sync warmup script can populate a cache an async runtime reads.

    Async cache parity on the same /data cassette:

    Path Sync get_game_data Async aget_game_data Notes
    Cold (fresh disk; full pipeline) 3,462 ms 4,291 ms asyncio.run per-iter loop construction; in a live event loop this overhead is gone.
    Disk-warm (new instance per call) 3,350 ms (1.0× vs cold) 3,973 ms (1.1× vs async cold) Identical underlying work; +~0.6 ms asyncio.to_thread overhead.
    In-memory warm (same instance) 0.0003 ms (10⁷×) 0.1034 ms (4.15×10⁴) Bench overstates async warm cost — each iter spins up a fresh event loop. Real per-call cost in a live loop is the same dict access (~0.0003 ms).

    The 4.15×10⁴ warm headline still clears the Phase 7 100–1000× target by 40×. Async users were locked out of GameDataCache in v3.0; v3.1 gives them the same disk + memo with the same correctness guarantees.

    v3.2 — StatCalc internals (bimorphic input + cached game_data)¶

    Runs on v3.2-research (off v3.1-research; v3.0 surface stays frozen per ADR-0001). Three orthogonal axes researched; two winners shipped per the pre-registered decision rule in ADR-0006. The other six candidates stay on throwaway prototype branches.

    What shipped

    Surface Measured Threshold Verdict
    A — StatCalc.calc_player_stats(player_struct) bimorphic +22.9 % vs dict input (5.2 ms on a 22.6 ms calc) ≤ 10 % Struct overhead OR ship floor option SHIPS (floor)
    E — get_statcalc_game_data(client, cache=cache) 25.74 ms → 3.62 ms cold-start (+85.9 %) ≥ 50 % cold-start improvement SHIPS

    What didn't

    Surface Measured Threshold Verdict
    B — partial-conversion adapter +21.4 % ≤ 10 % Struct overhead Defer (within ±1 % of A)
    C — accessor-subclass +23.6 % ≤ 10 % Struct overhead Defer (slightly worse than A)
    D — ProcessPoolExecutor fan-out 21.59 ms → 25.40 ms at 4w (0.85×) ≥ 2× speedup AND ≤ 1 % serial regression Defer (regresses)
    F — typed-Struct game_data tables ~+1.3 % (mechanism-bound; micro-bench, no prototype) ≥ 10 % hot-path Defer (mechanism-bound below threshold)
    G — direct v3.1 typed-segment consumption est. -5 % to +10 % (extrapolation from F's micro-bench; no prototype) ≥ 10 % hot-path Defer (negative-bound payoff)
    H — hot-table index restructuring +5.7 % targeted variant ≥ 10 % hot-path Defer (aggressive variant broke parity on mod-set bonuses)

    Key findings

    • Adapter cost is mechanism-bound by per-Mod conversion. All three bimorphic candidates (A/B/C) land within ±1 % of each other because the bulk of the work is msgspec.to_builtins walking the Mod sub-Structs. B's "skip Player metadata" saves ~0.3 ms; C's "interleave with calc" adds isinstance overhead that cancels the win. Conclusion: the simplest of the three (A) ships; the recipe recommends client.get_player(..., raw=True) for hot loops.
    • Parallelism is the wrong shape for this workload. Python's ProcessPoolExecutor IPC break-even (~500 µs/task even with batching) exceeds StatCalc's per-unit work (~70 µs). Parallel wins on player_small (1.6× at 4w) and loses on player_large (0.85× at 8w) — the result-pickle cost scales with batch size and the serial ship-pass tail eats into the chars-pass gain. Wait for either Cython inner loops (per-unit work grows) or sub-interpreters / free- threaded Python (IPC cost shrinks) before revisiting.
    • Cold-start is the single most leveraged optimization in StatCalc today. Just persisting the normalized form (no algorithmic change) gives 7× faster process startup. Big win for cron jobs and serverless callers; no-op for long-running bots.
    • Plan estimates ran consistently optimistic. Across Phases 2-4, none of the eight candidates exceeded its plan-stated payoff estimate; six fell short or failed entirely. The pre-registered decision rule (written before any measurement) was load-bearing for not shipping things that didn't pay back.

    v3.3 — StatCalc rewrite research (Phase 1 baseline, ADR-0007)¶

    Runs on v3.3-research (off v3.2-research; v3.0 surface stays frozen per ADR-0001). v3.3 is a broad research sweep — pure-Python restructure + native acceleration (Cython / mypyc / Rust) + algorithmic re-attacks of v3.2's H + a typed-fastpath for the bimorphic +22.9 % cost. Pre-registered decision rule lives in ADR-0007.

    Phase 1 baseline (recorded against v3.2 shipped code at SHA ef7a542):

    Metric Measured v3.3 ship threshold
    calc_player_stats(dict) warm, player_large (397 units) 21.8 ms Hot-path: ≤ 19.6 ms (≥ 10 % improvement)
    calc_player_stats(Player_struct) warm, bimorphic 27.4 ms (+25.8 %) Ergonomics: ≤ 22.9 ms (Struct overhead ≤ 5 %)
    cold_start: GameDataBuilder + StatCalc.__init__ 24.9 ms already shipped (Candidate E cached path: 3.6 ms)
    game_data resident size (asizeof, legacy dict tables) 12.9 MB Memory: ≤ 10.3 MB (≥ 20 % reduction)
    calc_player_stats transient peak, player_large 18.0 MB Informational — no bar
    msgspec.to_builtins(roster_unit) per-unit cost ~6.0 µs (Phase 4b typed-fastpath target — replace with direct getattr)

    Surprises from the Phase 1 measurement (vs. assumptions in the plan):

    • game_data is ~13 MB, not 50–100 MB. Plan over-estimated by ~5×. The ≥ 20 % reduction bar (≤ 10.3 MB target) is still meaningful but a smaller absolute win than imagined. Worth keeping as a metric; not worth blocking a ship on it alone.
    • _format_stats is the new #1 cProfile consumer, not _table_get. Cumulative time: _format_stats 119 ms (39 %) vs _table_get 85 ms (28 %). The v3.2 cProfile attribution noted _table_get because it was the loudest individual function; once you sum the inner work _format_stats does, it dominates. Phase 2's decomposition target is well-placed.
    • Bimorphic conversion confirmed as 100 % to_builtins. cProfile dump shows _to_dict_if_struct + msgspec._core.to_builtins together = 22 ms of the 330 ms profile run, exactly matching the bench's +25.8 % overhead. Phase 4b's typed-fastpath has a surgically clear target.

    Subsequent Phase 2–4 prototype branches measure against this baseline. Phase 5 will fill in the per-candidate matrix here once the integration commit lands.

    Phase 5 outcome (recorded against v3.3 integration HEAD):

    Surface Measured Threshold Verdict
    calc_player_stats(dict) warm, v3.3 integration 18.24 ms (+16.3 % vs v3.2 baseline 21.80 ms) ≥ 10 % hot-path SHIPS
    calc_player_stats(Player_struct) via typed-fastpath +10.1 % overhead (down from v3.2 +22.9 %) ≤ 5 % bimorphic Below bar; ships as partial-win
    game_data resident size unchanged at 12.9 MB ≥ 20 % Nothing shipped (no candidate targeted memory)

    Candidate matrix (all measured on player_large warm; v3.2 dict baseline = 21.80 ms):

    Candidate Branch Hot-path Ergonomics Verdict
    Phase 2 — pure-Python restructure pure-python-restructure +8.7 % — Ships combined
    Phase 3a — Cython + Phase 2 cython-prototype +17.8 % — Cleared but distribution cost too high — defer
    Phase 3b — mypyc + Phase 2 mypyc-prototype +15.0 % — Cleared but distribution cost too high — defer
    Phase 3c — Rust/PyO3 + Phase 2 rust-kernel-prototype est. ~+10-15 % — Mechanism-bound below Cython — defer
    Phase 4a — Candidate H re-attack not prototyped est. ~+5-8 % alone — Defer (covered by Cython in combined results)
    Phase 4b — typed-fastpath typed-fastpath — +10.1 % bimorphic overhead Ships as partial-win
    Phase 2 + 4b integration final-integration +16.3 % bimorphic +10.1 % (down from +22.9 %) SHIPS

    Key v3.3 finding: the 15-wheel-per-release native distribution matrix is the binding constraint on Cython/mypyc/Rust shipping, not their raw speed. All three cleared (or near-cleared) the 10 % hot-path bar, but for a research library serving a small SWGOH community the +6-9 percentage points of additional speed do not justify 30-60 min of CI per release tag. Pure-Python restructure + typed-fastpath together cleared the bar without the distribution complexity. Native variants stay on throwaway prototype branches as future options.

    • [ratelimit] + [circuitbreaker] extras — ADR-0004

    • ~~Async-aware GameDataCache for SwgohComlinkAsync~~ — landed in v3.1-research
    • ~~GameDataBuilder rewrite atop GameDataCache~~ — landed in v3.2-research as get_statcalc_game_data helper (ADR-0006)

    • stamina dependency — never added (Phase 2 hand-rolled the retry loop)
    • globals.py rename — collides with the builtin globals() function inside __init__.py; works today but is a known foot-gun

    What v3 delivered beyond plan¶

    • compat.to_pydantic(struct, model_class) — dynamic adapter without doubling the type surface. The plan called for as_model=True per endpoint method; the helper form serves the same need with zero kwarg explosion.
    • GameDataCache in-memory memo — the plan only specified disk caching. The realistic 10⁷× win comes from same-instance dict lookups; disk alone gives ~1×.

    Caveats¶

    • All numbers are on one machine. Phase-to-phase comparisons are valid (same hardware, same Python, same cassettes); cross-platform / cross-CPU comparisons aren't.
    • Timing benches drift 30–50% run-to-run on a working laptop. Memory baselines (deterministic — same bytes in, same allocations out) are the stable signal. Documented per-phase as an open question.
    • The Phase 3 plan's "Mann-Whitney U at p<0.05 on every comparative claim" was downgraded to "MWU only on Phase 3 headlines" (Plan D10). This report relies on consistent direction-of-change across multiple runs rather than statistical hypothesis testing per metric.
